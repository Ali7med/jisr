# ADR-0008 — منظومة TypeScript: سيرفر Fastify + ويب Next.js + هاتف Flutter

**الحالة:** ✅ معتمد
**التاريخ:** 2026-09-01
**يَنسَخ:** [ADR-0007](0007-dart-server-monorepo.md) (Dart للسيرفر · الويب من Flutter)

## السياق

اعتمد [ADR-0007](0007-dart-server-monorepo.md) لغة Dart للسيرفر بحجّة واحدة: إعادة استخدام طبقة التكاملات الجاهزة (`jisr_core`). مراجعةٌ لاحقة كشفت أن الحجّة أضعف مما بدت، وأن ثلاث حقائق تنقضها:

1. **لا SDK رسمية لـ Dart لخدمة رسائل Tuya.** الرسمية: Java · Go · Python · Node.js · C# ([Service SDKs](https://developer.tuya.com/en/docs/iot/server-sdk?id=Kbw09frvx48db)). الدفع الفوري — أهم مكسب من السيرفر ([ADR-0006](0006-central-server-platform.md)) — يصبح تنفيذاً يدوياً لبروتوكول Pulsar.
2. **نظام Dart الخلفي غير ناضج:** ORMs قاصرة، مكتبات شحيحة، وبصمة ذاكرة ~153MB ([تحليل 2026](https://medium.com/@ghimiresky2/is-dart-ready-for-backend-system-development-weighing-the-pros-and-cons-b46307798066)). و`shelf` بلا auth ولا ORM ولا DI.
3. **حجّة إعادة الاستخدام سقطت أصلاً** بقرار العميل الرفيع ([ADR-0009](0009-server-mandatory-thin-client.md)): الهاتف لن يحوي كود تكاملات إطلاقاً، فلا شيء يُعاد استخدامه.

## القرار

| القطعة | التقنية | اللغة |
|---|---|---|
| السيرفر | **Fastify** | TypeScript |
| لوحة الويب | **Next.js / React** | TypeScript |
| تطبيق الهاتف | Flutter (عميل رفيع) | Dart |
| `packages/shared` | تعريفات أنواع + عقود API | TypeScript |

**السيرفر والويب يتشاركان `packages/shared`** — تغيير حقل في استجابة API يكسر البناء في الطرفين فوراً بدل أن يُكتشف وقت التشغيل.

`Fastify` لا `NestJS`: الأخير موجّه «لفرق من ٣ مطوّرين فأكثر» وboilerplate أثقل، بينما Fastify «مناسب للفرق الصغيرة» بأداء أعلى (~45k مقابل ~28k طلب/ث) ([المقارنة](https://encore.dev/articles/nestjs-vs-fastify)).

## البدائل المرفوضة

| البديل | لماذا رُفض |
|---|---|
| **Dart/shelf** (القرار السابق) | لا SDK لرسائل Tuya · نظام خلفي غير ناضج · حجّة إعادة الاستخدام سقطت |
| **Go** | أخفّ استضافةً (ملف 15MB) وله SDK رسمية، لكن مكتبات auth/ORM أقل جاهزية والانتقال إليه من Dart أبعد. **الوصيف المعتمد** لو صارت تكلفة الاستضافة قيداً حاسماً |
| **Elixir/Phoenix** | الأفضل تقنياً للوقت الحقيقي (٢ مليون اتصال مقابل ١٠٠ ألف لـ Node)، لكن **لا SDK لـ Tuya**، ومنحنى التعلّم الأصعب، والسعة المطلوبة عندنا بضعة آلاف اتصال — هندسة زائدة |
| **Python/FastAPI** | مكتبة Tuya الأنضج، لكنه الأضعف في الاتصالات المتزامنة المستمرة (WebSocket) |
| **الويب من Flutter Web** | يوفّر كتابة الشاشات، لكن: حزمة 1.5–2MB · رسم على canvas بلا SEO · و**لوحة الإدارة ليست نسخة من شاشات الهاتف أصلاً** (ربط حسابات وأتمتة ومستخدمين مقابل تشغيل/إطفاء)، فالتوفير المفترض وهمي إلى حدٍّ بعيد |

## النتائج

### إيجابية
- SDK رسمية من Tuya للرسائل الفورية — لا تنفيذ بروتوكول يدوي
- كل ما نحتاجه جاهز: `Prisma` (ORM + migrations) · `BullMQ` (محرّك الأتمتة والجدولة) · `firebase-admin` (إشعارات) · `jose`+`argon2` · `@fastify/websocket`
- **أنواع مشتركة بين السيرفر والويب** — أمان تعاقدي حقيقي
- لوحة ويب خفيفة وسريعة، وSEO متاح لصفحة تعريفية لاحقاً
- TypeScript هو الأقرب ذهنياً لـ Dart بين كل البدائل

### سلبية
- **لغتان في المشروع** بدل واحدة — تنقّل ذهني بين Dart وTypeScript
- **إعادة كتابة تكامل Tuya بـ TypeScript** (~800 سطر): التوقيع، العميل، المترجم، عقد `Integration`. التصميم مثبت وموثّق فيبقى النقل ميكانيكياً، لكنه شغل حقيقي
- ثلاثة مشاريع تُطوَّر وتُنشر بدل اثنين
- Node أثقل ذاكرةً من Go — غير مؤثّر عملياً على VPS بـ 4GB

### ما يُبطل هذا القرار
- احتياج سعة اتصالات تتجاوز قدرة Node (>100k متزامن) ⇒ يُعاد تقييم Elixir
- صيرورة تكلفة الاستضافة قيداً حاسماً ⇒ Go
