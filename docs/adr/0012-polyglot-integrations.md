# ADR-0012 — سياسة التكاملات متعددة اللغات

**الحالة:** ✅ معتمد
**التاريخ:** 2026-09-02

## السياق

طموح المشروع «قوة Home Assistant»: تكاملات كثيرة ومتنوعة. أنضج نظام لمكتبات الأجهزة هو Python (نظام HA نفسه)، بينما سيرفرنا TypeScript ([ADR-0008](0008-typescript-stack.md)).

مثال واقعي: ربط إنفرتر Axpert عبر سحابة ShineMonitor/WatchPower، التي تغلّفها مكتبة Python غير رسمية ([shinemonitor-api](https://github.com/davidsmfreire/shinemonitor-api)).

القيد الحاكم: القاعدة 7 («إضافة شركة جديدة = ملف تكامل واحد + سطر في السجلّ») يجب ألا تنكسر مهما كانت لغة المكتبة المتاحة.

## القرار

**سلّم من ثلاث طبقات، يُصعَد فيه بالترتيب ولا يُقفَز:**

### الطبقة 1 — الافتراض: نقل البروتوكول إلى TypeScript
أغلب مكتبات الأجهزة السحابية غلاف رقيق حول HTTP + JSON + خدعة توقيع. المكتبة الأجنبية تُعامَل كـ**توثيق تنفيذي للبروتوكول**: تُقرأ، يُستخرج منها البروتوكول، ويُكتب تكامل TS أصيل في `server/src/integrations/<company>/`. يُثبَّت السلوك باختبارات على استجابات حقيقية مسجَّلة — فالـ API غالباً غير موثّق رسمياً، وأي تغيير من المزوّد يظهر في الاختبارات فوراً.

### الطبقة 2 — MQTT كناقل موحّد
منظومة كاملة تتحدث MQTT أو تُجسَّر إليه (Tasmota · zigbee2mqtt · ESPHome) ⇒ تكامل MQTT واحد يشتري عشرات الأجهزة دفعة واحدة. (الوصول المحلي نفسه محكوم بقرار «الوكيل المنزلي» المؤجّل — انظر أدناه.)

### الطبقة 3 — الاستثناء: حاوية جانبية (sidecar)
مكتبة عميقة فعلاً تستوفي **كل** الشروط الأربعة:
1. بروتوكول ثنائي/تسلسلي أو آلة حالات معقّدة — لا مجرد غلاف HTTP
2. لا مكافئ TS ناضج على npm
3. كلفة النقل تتجاوز ~أسبوعي عمل
4. المكتبة الأصلية مصانة ونشطة

⇒ تُشغَّل في حاوية خاصة بها ضمن Docker Compose الموجود، تكشف عقداً داخلياً بسيطاً (HTTP/WS: قائمة الأجهزة · قراءة حالة · تنفيذ أمر · دفع حدث)، ويستهلكها مندوب TS رفيع يحقق `Integration` — فتبقى القاعدة 7 صامدة. الأسرار تبقى في السيرفر؛ الحاوية عديمة الحالة ما أمكن؛ `/health` إلزامي.

**الوكيل المنزلي المستقبلي** (قرار «الوصول المحلي» الواجب قبل P7) يرث السلّم نفسه — ويجوز أن يُكتب هو نفسه بـ Python: ذلك يضع نظام مكتبات Python حيث يدفع أكثر ما يدفع (البروتوكولات المحلية: serial · Modbus · Zigbee) دون المساس بلغة السحابة.

## البدائل المرفوضة

| البديل | لماذا رُفض |
|---|---|
| **تبديل الباك كله إلى Python** | التكاملات القريبة كلها محايدة اللغة: Tuya لها SDK رسمي بالاثنين، ShineMonitor غلاف HTTP رقيق، وMQTT مكتباته ممتازة بالاثنين. ميزة Python الحقيقية في البروتوكولات المحلية العميقة — وهي خلف قرار الوكيل المنزلي أصلاً (الذي يجوز أن يكون Python). والتبديل يفقدنا `packages/shared` مع الويب (الذي سيبقى TypeScript بأي حال) ويعيد فتح كل قرارات 0008. والعامل الحاسم في مشروع فردي: **المطوّر أسرع في TypeScript** — إنتاجية الشخص الواحد تتفوق على أي حجة نظام بيئي (نوقش وحُسم 2026-09-02). **بند الإبطال أدناه يبقيه خياراً حياً بالأدلة لا بالحدس** |
| **استدعاء Python بـ child_process لكل طلب** | بلا إشراف ولا فحص صحة ولا عزل اعتماديات — هشاشة تشغيلية |
| **جسور FFI أو تحويل آلي للكود** | غير موثوقة لمكتبات حقيقية الحجم |
| **sidecar للجميع من البداية** | تضخم تشغيلي: حاوية لكل شركة يقتل بساطة «ملف تكامل واحد» ويستنزف الـ VPS |

## النتائج

### إيجابية
- القاعدة 7 تصمد مهما كانت لغة المكتبة المصدر
- ShineMonitor (طبقة 1) مرشّح طبيعي لـ«التكامل الثاني غير Tuya» — مقياس الستة أشهر في [الدراسة § 8](../01-study.md#٨-مقاييس-النجاح)
- الطبقة 3 تفتح كل نظام Python عند الحاجة الحقيقية بلا تغيير لغة المنصة

### سلبية
- نقل البروتوكول جهد لكل تكامل سحابي جديد — مقبول: هو في جوهره جهد **فهم** البروتوكول الذي لا مفرّ منه بأي لغة
- كل sidecar حاوية تُراقَب وتُرقَّى وتُؤمَّن — ولهذا هو استثناء مشروط لا خيار مريح

### ما يُبطل هذا القرار
لو انتهى **أغلب** التكاملات المشحونة فعلياً إلى sidecars رغم السلّم ⇒ اختيار لغة السيرفر نفسه كان خاطئاً لهذا المنتج — يُكتب حينها ADR ناسخ لـ [ADR-0008](0008-typescript-stack.md) مستنداً إلى الأدلة المتراكمة (أي التكاملات احتاجت sidecar ولماذا) لا إلى الحدس.
